🔐 Sumi — Customer/Mobile Auth API Documentation

Audience: QA/Testers and the Mobile App team (iOS/Android/Flutter/RN).
Scope: Modules/UserAuthManagement — phone + password authentication, OTP verification, social login (Google/Apple/biometrics), password reset, profile, phone change.

This document is generated directly from the current backend code (controllers, form requests, service, tests) — not from the old module README, which describes an email-based flow that no longer matches the implementation.

1. Base Information

Base URL {APP_URL}/api/frontend/auth (e.g. http://sumi-project.test/api/frontend/auth)
Content-Type application/json (use multipart/form-data only for the update-profile endpoint when uploading an image)
Auth scheme Authorization: Bearer {token} — Laravel Sanctum personal access tokens
Locale Send Accept-Language: ar or Accept-Language: en on every request (public routes only — once logged in, the account's preferred_language wins over the header). Any other value / missing header falls back to en.
Identity key Users are identified by country_code + phone (e.g. +966 + 512345678), not email.

Standard response envelope

Every endpoint (success or failure) returns this shape:

{
    "code": 200,
    "message": "Human readable message (localized per Accept-Language)",
    "errors": [],
    "data": { }
}
  • code — mirrors the HTTP status code.
  • errors — empty array on success. On validation (422) errors it is a list of { "key": "field_name", "value": ["message", ...] } objects (see §5). On other failures it's usually [] and the reason is in message.
  • data — endpoint-specific payload, null/absent on some endpoints.

HTTP status codes actually used

Status Meaning here
200 Success
401 Wrong password / missing or expired token (Unauthenticated)
403 Authenticated but wrong user type (e.g. a content-creator hitting a customer-only route)
404 Default error status for most business-logic failures — invalid OTP, user not found, blocked/suspended/deleted account, phone already in use, provider token owned by someone else, etc. (see §5). This is a backend quirk: don't assume 404 always means "route not found" — check the message.
422 Validation failed (missing/invalid fields)
500 Unexpected server error

⚠️ Tester note: A 404 from an auth endpoint almost never means "wrong URL" — read message. Only trust "route not found" if message literally says so.

2. Screen → API Flow Map

Mapped against the provided Figma/mockup screens (تسجيل الدخول, اضافه ال OTP, نسيت كلمة المرور, انشاء كلمة مرور جديدة).

A) Sign up (جمالك يبدأ هنا! → OTP → إنشاء كلمة مرور)

  1. User fills name + phone (+ optional referral code), accepts terms → POST /register
  2. App shows the 4-digit OTP screen → POST /verify-email with type: registration
    → response includes token immediately (user already exists, but is_complete_registeration = false)
  3. App shows "Create Password" screen → POST /set-password (auth required, use the token from step 2)
    → is_complete_registeration becomes true → show "Account created" success screen → go to app / login

B) Login (مرحباً بكِ في سومي)

  1. Phone + password → POST /login
    • If phone_verified_at is empty, backend silently sends a registration-style OTP instead of logging in (see §4.3) — the app should detect data.otp present + no token and route to the OTP screen instead of showing an "invalid login" error.
    • Otherwise returns token directly.
  2. Optional: Google / Apple / Face ID / Fingerprint buttons → POST /social-login

C) Forgot password (نسيت كلمة المرور → OTP → إنشاء كلمة مرور جديدة)

  1. Phone → POST /forget-password (type: password_reset, or omit — same default)
  2. OTP screen → POST /verify-email with type: password_reset → returns a short-lived reset_token (not a normal login token — it can only call reset-password)
  3. New password screen → POST /reset-password with Authorization: Bearer {reset_token}

D) Change phone number (inside profile, not in the provided screens but part of the module)

  1. POST /change-phone (auth) with the new phone only — country code is taken from the account
  2. OTP screen → POST /verify-phone-change (auth) with just the otp

3. Design vs. Backend — things testers should flag

Design (mockups) Backend (actual code) Impact
OTP screen shows 5 input boxes OTP is generated as a 4-digit numeric code (Otp::generate(..., length: 4, validity: 5min)) If the mobile app renders 5 boxes and pads/truncates incorrectly, verification will fail. Confirm with design whether OTP length should be bumped to 5 or the UI to 4.
Register screen only collects name + phone + referral code POST /register requires country_id (must exist in countries table) and accepts optional city_id; only country_code (dial code, e.g. +966) is visibly collected in the screen The app must resolve country_id some other way (e.g. from the phone-country picker) and send it — it's not optional.
Register screen has a single "Name" field Backend only stores name (no separate first/last name) No action needed, just confirming single field is correct
Login screen has a biometric icon next to the login button Biometric login maps to social-login with provider: face_id / fingerprint, but this requires the provider to have been connected first via POST /social-connections (there's no biometric enrollment screen in this batch) Make sure the app enables biometric login (social-connections) from an account/security settings screen at least once before showing the fingerprint icon as usable.
"نسيت كلمة المرور" OTP + reset flow Matches backend exactly (forget-password → verify-email type=password_reset → reset-password) ✅ No gap

4. Endpoints — Public (no Authorization header required)

4.1 Register 

POST /api/frontend/auth/register

Creates no database row yet — the payload is cached for registration_cache_ttl_minutes (default 60 min, see config/userauthmanagement.php) and only persisted once the OTP is verified. Calling register again for the same phone before verifying just overwrites the pending cache and resends a fresh OTP.

Body

Field Rules
name required, string, max 255
country_id required, integer, must exist in countries
city_id nullable, integer, must exist in cities
country_code required, string, max 10 (e.g. +966)
phone required, string, max 30, must be unique across users.phone and users.temporary_phone
terms required, must be true/1/"yes" (Laravel accepted rule)
referral_code optional, string, must exist in users.referral_code if provided
fcm_token optional, string
latitude, longitude optional, string
location_name, location_description optional, string
preferred_language optional, string, max 10 (ar/en) 
{
    "name": "Salma Mohamed",
    "country_id": 1,
    "country_code": "+966",
    "phone": "570151516",
    "terms": true,
    "referral_code": "kn33a1a"
}

Success (200)

{
    "code": 200,
    "message": "Registration successful. Please verify your phone with the OTP sent to your phone.",
    "errors": [],
    "data": {
        "otp": "4821",
        "registration": { "name": "Salma Mohamed", "country_id": 1, "...": "... (payload minus password)" }
    }
}

otp is returned in the JSON body directly (no real SMS is sent right now — sendOtpSms() is a no-op stub). This is expected in the current environment; use the returned otp to proceed. Flag to backend if SMS sending needs to go live before release.

Errors

  • 422 — missing fields, phone already taken, terms not accepted, country_id/referral_code don't exist.

4.2 Verify OTP 

POST /api/frontend/auth/verify-email

One endpoint, three purposes via type. type defaults to registration if omitted.

Field Rules
country_code required, string, max 10
phone required, string, max 20
otp required, string, exactly 4 characters
type optional, one of registration, password_reset, phone_update 
{
    "country_code": "+966",
    "phone": "570151516",
    "otp": "4821",
    "type": "registration"
}

Success — type: registration (creates the user, or activates it if it already existed unverified)

{
    "code": 200,
    "message": "Phone verified successfully.",
    "data": {
        "user": { "id": 12, "name": "Salma Mohamed", "user_type": null, "country_code": "+966", "phone": "570151516", "image": null, "preferred_language": "ar", "is_complete_registeration": false, "referral_code": "AB12CD" },
        "token": "1|abcdef123456..."
    }
}

is_complete_registeration is false here — the app must now call Set Password (§5.1) while authenticated with this token.

Success — type: password_reset

{
    "code": 200,
    "message": "OTP verified. You can now reset your password.",
    "data": { "reset_token": "2|xyz987..." }
}

Use reset_token only for POST /reset-password; it is a Sanctum token scoped to the reset-password ability and won't work as a normal auth token on other endpoints.

Success — type: phone_update (see §5.4) returns the updated user, no token.

Errors

  • 422 — malformed input (wrong OTP length, invalid type)
  • 404 — invalid/expired OTP, user not found, phone already verified (registration re-verify), account blocked/suspended/deleted

4.3 Login 

POST /api/frontend/auth/login
Field Rules
country_code required, string, max 10
phone required, string, max 20
password required, string
latitude, longitude optional, string
location_name, location_description optional, string
fcm_token optional 
{
    "country_code": "+966",
    "phone": "570151516",
    "password": "Aszasz1188#",
    "fcm_token": "device-fcm-token"
}

Success — normal login (200)

{
    "code": 200,
    "message": "Login successful",
    "data": { "user": { "...": "UserResource" }, "token": "1|abc...", "otp": null }
}

Success — but phone isn't verified yet (200, no token!)

{
    "code": 200,
    "message": "Phone not verified. Please verify your phone with the OTP sent to your phone.",
    "data": { "user": null, "token": null, "otp": "4821" }
}

The app must check for data.token === null on an otherwise-200 response and, if data.otp is present, route to the OTP screen (type: registration) instead of treating it as a successful login.

Errors

  • 422 — missing fields
  • 401 — wrong phone/password combination (Invalid credentials)
  • 404 — account is pending / blocked / suspended / deleted — message explains which

4.4 Social Login (Google / Apple / Face ID / Fingerprint) 

POST /api/frontend/auth/social-login

Handles both login and registration in one call: if provider + provider_token already exist, it logs in; otherwise it creates a brand-new, already-complete account (is_complete_registeration: true — no OTP/password step needed for social sign-ups).

Field Rules
provider required, one of google, apple, face_id, fingerprint
provider_token required, string (the OAuth id token / biometric key handle)
name required for new accounts, string, max 255
email optional, valid email, max 150
country_iso_code required for new accounts, 2-letter ISO code, must belong to an active country (e.g. SA, EG) — case-insensitive
latitude, longitude optional, string
fcm_token optional, string
image optional, image file, max 5MB
biometric_enabled optional, boolean
preferred_language optional, string, max 10 
{
    "provider": "google",
    "provider_token": "id-token-from-google-sdk",
    "name": "Jane Doe",
    "email": "jane@example.com",
    "country_iso_code": "SA",
    "fcm_token": "device-fcm-token"
}

Success (200) — same shape as login: { "user": {...}, "token": "..." }

Errors

  • 422 — country_iso_code missing/inactive/unknown for a first-time social sign-up
  • 404 — face_id/fingerprint used but never enrolled via social-connections first ("Biometric login is not set up...")

⚠️ Social accounts skip OTP entirely and are marked is_complete_registeration: true immediately, unlike phone registration.

4.5 Forgot Password 

POST /api/frontend/auth/forget-password
Field Rules
country_code required, string, max 10
phone required, string, max 20
type optional, registration or password_reset (default behavior = password reset) 
{ "country_code": "+966", "phone": "570151516" }

Success (200)

{ "code": 200, "message": "Password reset OTP sent to your phone", "data": { "otp": "4821" } }

Then continue with Verify OTP (type: password_reset, §4.2) to get a reset_token, then Reset Password (§5.2).

Errors

  • 422 — missing fields
  • 404 — user not found, or (with type: registration) no pending registration found for that phone / phone already verified

5. Endpoints — Protected (require Authorization: Bearer {token})

5.1 Set Password (completes registration) 

POST /api/frontend/auth/set-password

Auth: the token returned from Verify OTP / registration (§4.2).

Field Rules
password required, string, min 6, confirmed (send password_confirmation too) 
{ "password": "Aszasz1188#", "password_confirmation": "Aszasz1188#" }

Success (200)

{
    "code": 200,
    "message": "Password set successfully. Your registration is now complete.",
    "data": { "user": { "...": "UserResource", "is_complete_registeration": true } }
}

Errors: 422 validation, 401 missing/invalid token.

5.2 Reset Password 

POST /api/frontend/auth/reset-password

Auth: the reset_token from Verify OTP (type: password_reset) — not a normal login token.

Field Rules
password required, string, min 8, confirmed

Note the different minimum length vs. set-password (8 vs 6) — the mobile app's password-strength UI should validate against 8 here to avoid a false-positive on the client that then 422s on the server.

Success (200) — message only, no data. All existing tokens for the user are revoked (forces re-login everywhere).

{ "code": 200, "message": "Password reset successfully. Please login with your new password.", "errors": [], "data": null }

5.3 Update Profile 

POST /api/frontend/auth/update-profile

Use multipart/form-data if uploading image.

Field Rules
name sometimes, string, max 255
country_id sometimes, integer, exists
city_id sometimes, integer, must belong to the resolved country_id (submitted one or the user's current)
country_code sometimes, string, max 10
phone sometimes, string, max 30, unique — changing phone here does NOT trigger OTP re-verification; prefer change-phone (§5.5) for a verified flow
password sometimes, confirmed, min 6
image sometimes, image, max 5MB
latitude, longitude, location_name, location_description sometimes
preferred_language sometimes, string, max 10

Success (200)

{ "code": 200, "message": "Profile updated successfully", "data": { "user": { "...": "UserResource" }, "otp": null } }

Errors: 422 (e.g. city_id doesn't belong to country_id), 401.

5.4 Change Phone (two-step, OTP-confirmed — recommended over updating phone via §5.3) 

POST /api/frontend/auth/change-phone
Field Rules
phone required, string, min 5, max 30 — new phone only, country code comes from the account

Success (200): { "data": { "otp": "4821" } } — phone is staged on temporary_phone, not applied yet.

POST /api/frontend/auth/verify-phone-change
Field Rules
otp required, string, max 10

Success (200): applies the staged phone, sets phone_verified_at, returns updated user.

Errors (both): 404 if the number is already taken by another user, or if there's no pending change to confirm, or OTP is wrong/expired.

5.5 Social Connections (quick-login: Apple / Google / biometrics) 

GET /api/frontend/auth/social-connections

Lists all 4 providers with connection status (always 4 items: google, apple, face_id, fingerprint):

{
    "data": {
        "connections": [
            { "provider": "google", "label": "Google", "connected": true, "biometric_enabled": false },
            { "provider": "apple", "label": "Apple", "connected": false, "biometric_enabled": false },
            { "provider": "face_id", "label": "Face ID", "connected": false, "biometric_enabled": false },
            { "provider": "fingerprint", "label": "Fingerprint", "connected": false, "biometric_enabled": false }
        ]
    }
}

POST /api/frontend/auth/social-connections
Field Rules
provider required, one of the 4 values above
provider_token required, string, max 1000
biometric_enabled optional, boolean

Links (or re-links) the provider to the current account. Errors: 404 if that exact provider_token is already linked to a different user.

DELETE /api/frontend/auth/social-connections/{provider}

Unlinks a provider. {provider} must be one of the 4 valid values or the route 404s.

5.6 Logout 

POST /api/frontend/auth/logout

Revokes all Sanctum tokens for the user (all devices). No body needed.

{ "code": 200, "message": "User logged out successfully" }

5.7 Delete Account 

DELETE /api/frontend/auth/delete-account

Soft-deletes: sets status = deleted, is_active = false, revokes all tokens. No body needed. Show a confirmation dialog client-side before calling this — it's irreversible from the app's perspective.

5.8 Type-Guarded Profile 

GET /api/frontend/auth/customer/profile        (requires user_type = customer)
GET /api/frontend/auth/content-creator/profile (requires user_type = content_creator)

Returns the user with country and city relations loaded. Calling the wrong one for your account type returns 403 Unauthorized, not 404.

7. The user object (UserResource)

Returned by register-verify, login, social-login, set-password, update-profile, verify-phone-change, etc.

{
    "id": 12,
    "name": "Salma Mohamed",
    "user_type": "customer",
    "country_code": "+966",
    "phone": "570151516",
    "image": "https://.../users/xxx.jpg",
    "country": { "id": 1, "name": "Saudi Arabia", "flag": "🇸🇦" },
    "city": { "...": "only present if loaded, e.g. on the customer/content-creator profile endpoints" },
    "preferred_language": "ar",
    "is_complete_registeration": false,
    "referral_code": "AB12CD"
}

user_type is null until the account completes registration/onboarding elsewhere in the product (it's set outside this module). country/city are only populated when explicitly eager-loaded (only true for customer/profile and content-creator/profile).

8. QA Test Checklist

Registration

  • Register with all required fields → 200, OTP in data.otp, no row in users table yet
  • Register with missing name/country_id/phone/terms → 422
  • Register with terms: false → 422
  • Register twice with the same phone before verifying → succeeds both times (cache overwritten), only one user created after verification
  • Verify OTP with correct code → 200, user created with is_complete_registeration: false, token returned
  • Verify OTP with wrong/expired code → 404
  • Verify with an OTP that isn't 4 digits → 422
  • Register with a referral_code that belongs to an existing user → after verification, a referrals row exists and the referrer's loyalty progress advances
  • Set password with a valid token → 200, is_complete_registeration: true
  • Set password without a token → 401

Login

  • Correct phone+password, verified account → 200 with token
  • Correct phone+password, unverified account → 200, token: null, otp present — app must reroute to OTP screen
  • Wrong password → 401
  • Blocked/suspended/deleted/pending account → 404 with an explanatory message

Forgot / Reset password

  • Forgot-password for existing phone → 200 with OTP
  • Forgot-password for unknown phone → 404
  • Verify OTP type=password_reset → reset_token returned (not a normal token)
  • Reset password using reset_token → 200, all previous sessions/tokens invalidated (verify old token now gets 401)
  • Reset password using a normal login token instead of reset_token → should fail (wrong ability) — verify this is actually enforced end-to-end, not just "seems to work"
  • Password shorter than 8 chars on reset → 422 (vs. 6 chars on set-password — confirm this asymmetry is intended)

Social login

  • New Google/Apple user with valid country_iso_code → 200, account created and already complete (no OTP step)
  • New social user with inactive/unknown country_iso_code → 422
  • Existing provider+provider_token → logs in as that user, no duplicate account created
  • face_id/fingerprint login without prior enrollment → 404 ("Biometric login is not set up")
  • Reusing a provider_token already linked to a different user (via social-login or social-connections) → 404

Phone change

  • Request change to a free number → 200, OTP sent, phone unchanged until verified
  • Request change to a number already used by another user → 404
  • Verify with correct OTP → phone applied, phone_verified_at updated
  • Verify with no pending change staged → 404

Access control

  • Content-creator hitting /customer/profile → 403
  • Customer hitting /content-creator/profile → 403
  • Any protected endpoint without/with expired token → 401

Localization

  • Same request with Accept-Language: ar vs en → message text changes language accordingly
  • Once logged in, does the account's preferred_language override the header? (per HandleLang middleware — worth a dedicated regression check since the header is normally what testers control)

9. Quick cURL reference 

# 1. Register
curl -X POST "$BASE/api/frontend/auth/register" \
  -H "Accept-Language: ar" -H "Content-Type: application/json" \
  -d '{"name":"Salma","country_id":1,"country_code":"+966","phone":"570151516","terms":true}'

# 2. Verify OTP
curl -X POST "$BASE/api/frontend/auth/verify-email" \
  -H "Content-Type: application/json" \
  -d '{"country_code":"+966","phone":"570151516","otp":"4821","type":"registration"}'

# 3. Set password (use token from step 2)
curl -X POST "$BASE/api/frontend/auth/set-password" \
  -H "Authorization: Bearer {token}" -H "Content-Type: application/json" \
  -d '{"password":"Aszasz1188#","password_confirmation":"Aszasz1188#"}'

# Login
curl -X POST "$BASE/api/frontend/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"country_code":"+966","phone":"570151516","password":"Aszasz1188#"}'
